# 每节点连接数评估

[文档目录](README.md) · [性能基准](performance.md) · [Session 总额度](session-limits.md)

本页是开发分支的短时测量入口。Session 当前默认每节点一条物理连接。[Java Driver 的连接池指南](https://apache.github.io/cassandra-java-driver/4.19.0/core/pooling/)同样默认单连接，并要求依据具体测量调整连接数；协议可以在一条连接上复用多个 stream，不能由连接数量直接推断吞吐收益。

可配置接口与恢复语义见[每节点连接池](pooling.md)。

## 同条件比较

```sh
python scripts/pooling_evaluation.py --trials 3 --server-description "实际的客户端、服务端、JVM堆和CPU、网络环境"
```

使用常规 `CQL_HOST`、`CQL_PORT`、`CQL_USERNAME`、`CQL_PASSWORD`。该命令会创建或覆盖专用 **mooncql_bench.probe** 测试分区，需要 DDL 与读写权限，只能连接测试实例。服务端当前要求 Cassandra 5.0.5。

入口复用 `cmd/bench`，在同一个 release 二进制中比较同一节点的 **1、2、4 条连接**。每组保持总并发不变，最大 128，每次操作最多一个实际 RPC 在途；每条连接独立 PREPARE，不跨连接借用句柄。这里测量的是低层连接数据通道，可用于决定是否增加 Session 连接池配置。

增加 `--session` 使用 [cmd/poolbench](../cmd/poolbench/main.mbt) 测量真实 Session 池。该入口固定总 RPC 上限 128、等待上限 128，独立记录连接数量和后台任务，并在排空后断言资源归零。报告以 `uses_session_pool` 区分入口；低层原型将一次操作固定在一条物理连接上，Session Pager 每页按实际调度选择连接。应在同一入口内比较连接数，避免混用两个入口的绝对吞吐。

完整矩阵有十二个场景，每种连接数至少三轮：64 字节读取的并发 32／128、64 字节写入的并发 128、400000 字节随机数据读取和写入的并发 32，以及 64 字节、页大小 4 的分页；各包含普通帧与 LZ4。随机种子固定为 2026102301，同一场景的三种连接数交错执行，场景与轮次也打乱顺序。

可用重复的 `--case-id` 选择完整矩阵中的场景进行针对性复测，并以 `--count-scale` 将该场景的操作数统一放大 1–16 倍。报告保留原场景编号、选择范围和放大倍数；选定场景的结果只解释该范围，不能代替完整矩阵。

连接建立、建表、九行初始数据、每条连接的准备及八次总预热操作均在计时和进程 CPU 区间之前。读与分页逐字段核对数据，写入检查结果并在末尾读取核对；每条连接结束时断言 pending 和等待请求为零。所有连接都由嵌套作用域关闭，部分建连失败也回收已有连接。

纯编解码和纯压缩场景仍通过原有 [benchmark.py](../scripts/benchmark.py) 运行；它显式固定单连接，避免环境中的 `BENCH_CONNECTIONS` 改变历史基线条件。直接运行 `cmd/bench` 时，该变量可选 1–8，默认 1，并写入结果。

## 本地短时测量与默认值决策

2026-10-23 在 Windows 11 原生客户端连接同机 WSL Ubuntu 的 Cassandra 5.0.5，服务端 JVM 堆 1 GiB、`ActiveProcessorCount=2`、无认证、回环 TCP 的条件下，完成低层入口和真实 Session 各十二场景三轮，以及分页场景各五轮放大复测，共 276 组正式样本。报告均通过数据、矩阵完整性和资源回收断言；这些是短时测试。

真实 Session 的放大复测固定并发 32、64 字节值、九行分区、页大小 4，每轮完成 8192 次完整遍历。下表的吞吐和 P99 为五轮中位数；比率为多连接中位数除以单连接中位数，原始报告另保留逐轮配对比率。CPU 为客户端测量区间 CPU 时间／墙钟时间，100% 约等于一个核，RSS 为各轮进程峰值的中位数。

| 帧 | 每节点连接 | 遍历／秒 | 吞吐比率 | 遍历 P99 比率 | 客户端 CPU | 峰值 RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 普通 | 1 | 4073 | 1.000 | 1.000（18.27 ms） | 93.9% | 10.9 MiB |
| 普通 | 2 | 4115 | 1.010 | 0.552 | 98.6% | 10.8 MiB |
| 普通 | 4 | 4151 | 1.019 | 0.544 | 97.7% | 10.8 MiB |
| LZ4 | 1 | 3818 | 1.000 | 1.000（20.89 ms） | 94.3% | 10.8 MiB |
| LZ4 | 2 | 3756 | 0.984 | 0.588 | 98.5% | 10.9 MiB |
| LZ4 | 4 | 3974 | 1.041 | 0.489 | 98.3% | 10.9 MiB |

较短的真实 Session 全矩阵中，四连接的分页吞吐中位数提高约 21%–23%；放大复测后，普通帧四连接的各轮吞吐比率范围为 0.931–1.039，LZ4 为 0.936–1.207，提升并不稳定。两种帧的多连接遍历 P99 在五轮中均下降。多数小查询没有收益，有些写入尾延迟更差。因此**默认保持一条连接**；有分页尾延迟需求的负载可按相同方法试验两条，再比较四条，不能据此宣称普遍吞吐提升。

该测量关闭心跳以隔离数据通道成本，一节点一／二／四连接对应三／七／十三个后台任务句柄。启用默认心跳还会增加每连接心跳任务，发现控制连接另计。RSS 的小幅变化处于本机波动范围，不代表增加连接没有资源成本。客户端与服务端共用宿主机，未采集服务端 CPU，无法据此证明服务端饱和或确定生产服务器规格。跨主机、真实分区分布和实际 TLS／认证配置仍须重新测量。

复测命令：

```sh
python scripts/pooling_evaluation.py --session --trials 5 --case-id 5 --case-id 11 --count-scale 8 --server-description "实际测试环境"
```

## 产物与解释

每组记录吞吐、P50／P95／P99、进程 CPU 时间和峰值常驻内存。CPU 和请求时长只计测量区间；峰值内存覆盖整个进程，包含连接与预处理对象的成本。分页还报告单页延迟分位数。所有轮次写入 `.artifacts/pooling-evaluation-*/records.jsonl`，日志与最终 `result.json` 保留工具链、源码指纹、生成 C 摘要、场景、实际连接数和环境说明。

汇总保留每项指标的中位数与全范围，并给出同轮相对于单连接的吞吐／P99 比率。中位 P99 是各轮 P99 的中位数，不是合并请求样本的总体 P99。数量、连接数、压缩选项、并发、非有限数、无效尾延迟或缺少内存测量均使验收失败；缺轮或重复轮次也不能生成通过报告。

这些场景使用固定测试分区和热点行，报告客户端成本，未采集服务端 CPU、磁盘或网络饱和度。解释时须检查每轮波动、吞吐和尾延迟是否同时稳定改善，以及资源代价；平台或服务端受限时，应先补充对应资源观测，不能把平台瓶颈归因于连接数。最终池大小决策应针对实际负载复测。

CI 的 `--smoke` 只执行一个短小读取场景、三种连接数各一轮，报告明确标记 `smoke=true`。它检查入口和数据正确性，不构成性能结论：

```sh
python scripts/pooling_evaluation.py --smoke
python scripts/pooling_evaluation.py --session --smoke
```

原始性能日志和样本不进入 Git 源码提交；CI 将冒烟产物作为构建附件归档。连续六小时混合负载与周期故障测试仍按待办最后一项暂缓。
