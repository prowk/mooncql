# 预处理缓存与并发准备

本文描述 main 分支；新增缓存策略尚未发布到 0.1.0。

`Config::new(prepared_cache_capacity=64)` 设置每个连接的 LRU 容量，允许 0 至 65536，默认 64。0 禁用常驻缓存，但同时等待同一语句准备的调用仍合并为一个 PREPARE。缓存键包含完整 CQL 与准备时的 keyspace。命中会刷新最近使用顺序；超过容量淘汰最久未使用的条目。

淘汰只移除驱动的缓存引用，已返回的 Prepared 继续有效。服务端单独管理自己的缓存；只有收到匹配 ID 的 UNPREPARED，执行才会重新 PREPARE 并恢复一次。SessionPrepared 的每节点状态同样可以继续持有已从连接缓存淘汰的 Prepared。

每个 CQL/keyspace 使用独立的合并状态。相同语句的并发请求共享一次准备结果，不同语句可以同时发送，避免一条慢准备语句阻塞其他语句。准备失败会向本批等待者返回同一失败，最后一个调用退出后清除状态，后续调用可重新准备。

取消某个等待者不会取消当前准备请求。准备请求的调用方自身取消后，其他等待者可以接手并重新发起幂等的 PREPARE；已经完整发送的旧请求仍占用 stream，其迟到响应会被吸收，不覆盖新的缓存结果。该行为只适用于 PREPARE，不代表驱动会重放业务写入。

等待同一语句的调用计入连接的有界等待数量和字节预算，并受各自总截止时间约束。不同语句的准备状态数量、CQL 编码总量也有上限，避免在实际网络准入前堆积无界状态。连接关闭会清空缓存和准备状态，打断缓存与 Connection 的引用环。`prepared_cache_size()` 可读取当前常驻条目数。

Prepared 与 SessionPrepared 自动在 EXECUTE 中继承准备时的 keyspace，并拒绝显式冲突的 keyspace；绑定值在等待前冻结。建议使用完整限定表名或明确的准备 keyspace，避免并发 USE 产生连接上下文竞态。

回归验证 LRU 命中顺序、淘汰后原对象可执行、禁用缓存时的合并、不同语句独立准备、失败共享与后续重试、等待者取消、准备调用方取消及迟到结果，以及合并等待的截止时间和队列上限。

请求 custom payload 也属于准备内容，相同 CQL／keyspace／payload 才共享缓存与并发准备；trace 标志不改变缓存键。prepare_with_info 在缓存命中时标记 cached=true、attempt_count=0，并保留最近实际 PREPARE 的响应信息。
